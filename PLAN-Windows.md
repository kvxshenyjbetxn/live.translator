# План підтримки Windows

Мета: запустити Live Translator на Windows, зберігши підтримку macOS і поточні можливості програми.

Початкова ціль: Windows 11 x64. Інші версії Windows та ARM64 — поза початковим обсягом.

## 1. Перевірити базову збірку

- [x] За окремим погодженням встановити залежності npm через `npm ci`.
- [x] Виконати `npm run check`, `npm run build` та перевірити тести на Windows.
- [x] Виконати Rust-перевірки для `x86_64-pc-windows-msvc`.
- [x] Виявити й усунути помилки Windows-компіляції, не змінюючи поведінку macOS.
- [x] Перевірити запуск Tauri: користувач підтвердив запуск Windows GUI; агент GUI не запускав.

Результат: `npm ci`, `npm run check` і `npm run build` успішні; `npm run test` — 98 пройшли, 3 macOS shell-тести пропущено на Windows. `cargo check --workspace --all-targets --target x86_64-pc-windows-msvc` і `cargo test --workspace --target x86_64-pc-windows-msvc --locked` успішні (67 тестів). `npm run tauri -- build --no-bundle --target x86_64-pc-windows-msvc` успішно скомпілював release без запуску чи пакування. Помилок Windows-компіляції не виявлено; виправлено Windows-сумісність тестів. macOS-збірку та shell-тести на Mac не перевірено. `npm ci` повідомив про 3 low severity вразливості.

Критерій: Windows-збірка компілюється; інтерфейс запускається після дозволеної ручної/GUI-перевірки. Це ще не означає, що захоплення аудіо працює.

## 2. Додати Windows-джерела та захоплення звуку

- [ ] Додати Windows-модуль у `crates/translator-core/src/capture/`, залишивши `macos.rs` окремим і працездатним.
- [ ] Реалізувати список програм зі звуком, стабільні ідентифікатори та перевірку актуальності процесів.
- [ ] Передбачити багатопроцесні програми, зокрема браузери, без подвійного захоплення звуку.
- [ ] Реалізувати WASAPI Process Loopback для вибраної програми/дерева процесів.
- [ ] Передавати PCM у наявні аудіочерги з коректною обробкою формату, тиші та помилок.
- [ ] Заборонити захоплення власного звуку Live Translator.
- [ ] Коректно звільняти Windows-аудіоресурси при зупинці, помилці та закритті програми.

Критерій: захоплюється лише вибране джерело, без інших програм і без зворотного захоплення перекладу.

Поточний стан stage 2: список аудіосесій охоплює активні вихідні пристрої; ідентичність процесів перевіряється за PID та часом запуску. Windows Process Loopback підключений для одного дерева процесів, незалежні корені відхиляються з поясненням. Користувач підтвердив, що реальний переклад Windows добре працює в одному базовому сценарії; інші сценарії, зокрема ізоляція, тиша й очищення, залишаються неперевіреними. Пункти не позначені завершеними до ручної перевірки.

## 3. Узгодити керування оригінальним звуком

На macOS джерело приглушується на час захоплення, а програма відтворює власний мікс оригіналу й перекладу. Користувач погодив Windows UX: оригінал залишається у програмі та системному мікшері; Live Translator відтворює лише переклад. Оригінал не приглушується і повзунок оригіналу на Windows не показується. Користувач підтвердив лише базовий сценарій реального перекладу; відсутність дублювання в усіх сценаріях окремо не перевірена.

- [x] Погоджено UX лише перекладу: Windows не змінює гучність і не приглушує джерело, тому нативне відновлення не потрібне. Незалежне керування гучністю оригіналу на Windows відкладено.
- [ ] Ручна перевірка гучності, відсутності дублювання та поведінки при зупинці й помилках.

Критерій: регулятори й звук відповідають погодженій поведінці Windows; ручна перевірка залишається відкритою.

## 5. Адаптувати інтеграцію з робочим столом

- [x] Реалізовано визначення активної програми Windows через snapshot foreground-вікна та executable процесу; автоматичні тести використовують підставні дані.
- [x] Ідентифікатор збігається зі списком аудіосесій за повним шляхом executable без урахування регістру.
- [ ] Перевірити глобальну гарячу клавішу, конфлікти комбінацій і обидва режими вибору джерела.
- [ ] Перевірити трей, закриття вікна, повторне відкриття, збереження налаштувань та відкриття їхньої папки.

Foreground PID може відрізнятися від PID аудіопроцесу браузера: однаковий executable дає збіг, інший helper executable не вгадується і не зіставляється з предками. Без відповідної аудіосесії запуск відхиляється; відсутній/недоступний процес та власне вікно теж не вибираються. Незалежні аудіокорені залишаються непідтриманими. Ручна Windows-перевірка гарячої клавіші й macOS-перевірка ще потрібні.

Критерій: на Windows працюють наявні сценарії керування, без регресій у macOS-гілках.

## Правила виконання

- Рухатися послідовно; позначати пункт виконаним лише після відповідної перевірки.
- Зберігати спільну логіку перекладу, інтерфейсу й аудіо там, де вона справді кросплатформна.

## Перевірка гучності Windows Process Loopback

- Контрольований CLI-експеримент на Windows 10.0.26200.8037: окремий дочірній процес відтворював лише синтетичний тон 440 Гц, захоплення було обмежене його перевіреним PID/деревом, зміни — лише його унікальною однопроцесною аудіосесією. Початкові гучність і mute відновлено успішно.
- За підтвердженої гучності сесії 1.0 / 0.5 / 0.0 RMS захопленого PCM становив 0.056569 / 0.028284 / 0.000000 (peak 0.080000 / 0.040000 / 0.000000); при mute RMS і peak також 0, після unmute повернулися до 0.056569 / 0.080000. В усіх етапах рендерер працював і зчитано 115200 семплів.
- Висновок для цього ПК і цього сценарію: керування гучністю або mute сесії джерела знижує/глушить і вхід перекладу. Тому пряме керування сесією не задовольняє незалежність гучності; повзунок оригіналу Windows не реалізовано. Фактичне послаблення звуку на виході окремо не вимірювалося; результати не доводять поведінку всіх конфігурацій Windows.
